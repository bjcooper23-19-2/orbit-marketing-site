## Existing hosting and domain boundary

GitHub reports has_pages: false for bjcooper23-19-2/orbit-marketing-site, and its Pages API returned 404. The repository already has a manual workflow_dispatch Pages workflow, now aligned with GitHub's configure, upload and deploy actions. It has not been run.

Public DNS currently answers 185.158.133.1 for both myfamilyorbit.uk and www.myfamilyorbit.uk; these are observed public answers, not an export of the Cloudflare zone. Public MX records use Cloudflare Email Routing. Both the apex and www return HTTP 301 to https://app.myfamilyorbit.uk/. The apex /privacy/ and /terms/ paths also redirect to the corresponding app paths. The Tally privacy link therefore does not currently reach this marketing policy, and its completion redirect currently goes to the app. This is a release blocker, not a reason to alter the live routing without a plan.

Inspect the actual Cloudflare zone and product link requirements before a cutover. In particular, confirm whether existing application links, account or email flows depend on apex redirects. Preserve app, admin, notify, email-routing and Resend records. Do not assume the apex can be replaced merely because the app also has a subdomain.

Review a separate release change that removes the unconditional publicationApproved guard and sets publication controls for indexing. Keep review restrictions until this point.

If the apex cannot move, revise the proposed hosting/canonical plan rather than repointing it silently. Export or record current DNS and redirect settings before any authorised change.
3. After merge is explicitly authorised, enable GitHub Pages in repository Settings → Pages with GitHub Actions as the source. The current repository has no enabled Pages site. Run the manual workflow only after publication approval and verify the default Pages URL first. The workflow uploads dist/ and deploys through the protected github-pages environment.
4. In GitHub Pages settings, add and verify myfamilyorbit.uk as the custom domain before changing DNS. With an Actions deployment, a repository CNAME file is not required. Retain any GitHub verification TXT record. [GitHub's custom-domain guide](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/managing-a-custom-domain-for-your-github-pages-site) gives the current requirements.
5. Only after the apex conflict is resolved and DNS change separately authorised, replace the conflicting apex routing with the chosen GitHub Pages records. GitHub currently documents four IPv4 A targets: 185.199.108.153, 185.199.109.153, 185.199.110.153 and 185.199.111.153; [Cloudflare's apex CNAME flattening](https://developers.cloudflare.com/dns/cname-flattening/) may instead support an approved CNAME. Do not retain a conflicting old apex record. Decide www behaviour separately and, if used, replace its current app routing with a CNAME to bjcooper23-19-2.github.io. Do not change MX, SPF, DKIM, DMARC, app or Resend records.
6. Wait for DNS and certificate provisioning; enable HTTPS in Pages. Verify the apex, /privacy/, /terms/, www behaviour, all registration links, Tally's privacy link and return destination, contact delivery, the app and its existing email flows. Check social previews and the sitemap. Keep a tested rollback route until the cutover is accepted.
